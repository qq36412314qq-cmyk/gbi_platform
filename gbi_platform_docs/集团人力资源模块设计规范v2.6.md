## 一、模块概述

### 1.1 设计原则

| 原则 | 说明 |
|------|------|
| 多租户隔离 | 所有业务数据通过 `company_id` 字段实现子公司级数据隔离 |
| 审批引擎复用 | 入职/转正/调岗/离职统一走 `flowEngineService.submit()`，流程定义在 `flow_definition` 表中配置 |
| 快照字段 | 关键展示字段（姓名、组织名称、岗位职级等）在写入时固化，避免关联数据变更导致历史失真 |
| 逻辑删除 | 所有业务表采用 `is_delete` 软删除，保留完整审计轨迹 |
| 权限分级 | 操作类接口统一通过 `@PreAuthorize` + `PermissionConst` 权限标识控制，敏感操作（薪资修改、离职）强制审计日志 |
| 敏感信息加密 | 身份证号、手机号、工资卡号采用 AES 密文存储，VO 层统一脱敏返回 |
| 员工-用户联动 | `hr_employee.user_id` 与 `sys_user.id` 双向关联，离职自动禁用账号 |

### 1.2 技术栈

| 层级 | 技术选型 |
|------|---------|
| 后端 | Java 21 + Spring Boot 3.5.3 + MyBatis-Plus |
| 前端 | Vue 3 + TypeScript + Element Plus + Vite |
| 数据库 | MySQL 8.0（utf8mb4 字符集） |
| 审批引擎 | 统一 flow_engine 服务（流程定义/实例/任务，表驱动轻量引擎） |

### 1.3 模块归属类型

| 子功能 | 归属类型 | 说明 |
|--------|---------|------|
| 组织岗位 | 全集团共享（双向数据隔离） | 集团看全量，子公司仅看自身 |
| 员工档案 | 全集团共享（双向数据隔离） | 集团 HR 查看全部；子公司 HR 仅本单位；普通员工仅个人数据 |
| 人事异动 | 全集团共享（双向数据隔离） | 同上 |
| 考勤管理 | 全集团共享（双向数据隔离） | 读取公共 `oa_clock_record` 表聚合 |
| 薪酬薪资 | 全集团共享（双向数据隔离） | 薪资推送到财务后，财务侧独立记录 |
| 社保公积金 | 全集团共享（双向数据隔离） | 同上 |

### 1.4 模块边界

HR 模块（`hr_*` 系列表 + 复用 `oa_*` / `biz_*` / `flow_*` / `sys_*`）
- 员工主档案（`hr_employee`）
- 岗位管理（`hr_post`）
- 员工附件（`hr_employee_file`）
- 人事异动申请（`hr_entry_apply` / `hr_regular_apply` / `hr_transfer_apply` / `hr_resign_apply`）
- 考勤汇总（`hr_attendance_record`，聚合自 `oa_clock_record`）
- 请假记录（`hr_leave_record`，同步自 `oa_leave_apply`）
- 薪资档案（`hr_salary_archive`）
- 月度薪资核算（`hr_salary_month`）
- 社保公积金台账（`hr_social_security`）

## 二、和现有系统关键联动

### 2.1 中台用户体系（sys_user）
- **不新建用户表**。HR 员工档案通过 `user_id` 字段关联 `sys_user.id`（可空）。
- 员工离职 → 自动调用 `SysUserService.disableUser()` 将关联的 `sys_user.status = 0`；账号删除不影响人事档案。
- 入职审批通过 → 可选一键生成系统账号（`user_id` 写入，`username/password` 由 HR 初始化）。

### 2.2 统一审批引擎（flow_*）

所有人事异动统一调用 `FlowEngineService.submit(defCode, sourceType, sourceId, title)`，流程定义在 `flow_definition` 表配置，业务类型编码如下：

| 业务类型 | 流程定义 def_code | 审批通过动作 |
|---------|------------------|------------|
| 入职 | `hr_entry` | 写入 `hr_employee`；若 `auto_create_user=true`，写入 `sys_user`，`hr_employee.user_id` 回填 |
| 转正 | `hr_regular` | 更新 `hr_employee` 状态和转正日期 |
| 调岗 | `hr_transfer` | 更新 `hr_employee` 部门和岗位 |
| 离职 | `hr_resign` | 更新 `hr_employee` 状态为离职，禁用 `sys_user` |

> 说明：流程定义编码与 `CommonConst` 中 `FLOW_DEF_HR_*` 常量对齐，禁止在业务代码中硬编码字符串。

所有申请表单字段均需带 `flow_instance_id`，状态枚举对齐现有规范：
```
0=草稿  1=审批中  2=已通过  3=已驳回  4=已撤回
```

### 2.3 财务模块（biz_recv_pay_plan / biz_finance_flow）
- 薪资核算通过后，按员工批量写入 `biz_recv_pay_plan`（`biz_type=salary`，`direction=2 应付`）。
- 财务支付后，自动生成 `biz_finance_flow`（`business_type=salary`），保留快照字段（姓名、公司、金额）。
- 薪资发放记录不关联摊位/商户，仅关联 `employee_id` 和 `company_id`。

### 2.4 公共打卡记录（oa_clock_record）
- OA 打卡记录表 `oa_clock_record` 已存在，HR 考勤汇总直接从该表按 `company_id + user_id` 聚合。
- HR 侧无需另建打卡原始表，避免数据重复。
- HR 考勤统计（月报、异常标记）在 `hr_attendance_record` 中独立生成快照。

## 七、关键业务逻辑说明

### 7.1 员工与用户联动
| 事件 | 操作 |
|------|------|
| 入职审批通过 | 写入 `hr_employee`；若 `auto_create_user=true`，调用 `SysUserService.createUser()` 写入 `sys_user`（状态=1），`hr_employee.user_id` 回填 |
| 离职审批通过 | `hr_employee.employee_status=3`；查找关联 `sys_user`，调用 `SysUserService.disableUser()` 设 `status=0`（禁用） |
| 删除 sys_user | 不删除 `hr_employee`，仅置 `user_id=NULL`，保留人事档案 |

### 7.2 审批通过动作（HrTransferService）
所有异动统一调用 `FlowEngineService.submit(defCode, sourceType, sourceId, title)`：
- `def_code=FLOW_DEF_HR_ENTRY` → 通过后调 `HrEmployeeService.createFromEntry()`
- `def_code=FLOW_DEF_HR_REGULAR` → 通过后更新 `hr_employee.regular_date` 和 `employee_status`
- `def_code=FLOW_DEF_HR_TRANSFER` → 通过后更新 `hr_employee.org_id`、`post_id`，同步写入 `post_level` 快照
- `def_code=FLOW_DEF_HR_RESIGN` → 通过后更新 `hr_employee.employee_status=3` + 禁用 `sys_user`

### 7.3 考勤聚合（HrAttendanceService.syncMonthly）
每月定时任务或手动触发：
1. 按 `company_id` + `attendance_month` 聚合 `oa_clock_record`
2. 关联 `hr_leave_record` 扣减应出勤天数
3. 写入 `hr_attendance_record` 快照（迟到/早退/缺卡/请假/旷工分类）
4. 异常数据（缺卡>2天）写审计日志

### 7.4 薪资推送到财务（HrSalaryService.pushToFinance）
薪资核算通过后：
1. 为每个员工写入 `biz_recv_pay_plan`（`biz_type=salary`，`direction=2 应付`）
2. 财务支付后，自动生成 `biz_finance_flow`（`business_type=salary`，含姓名快照）
3. 更新 `hr_salary_month.pay_status` 和 `pay_time`

## 十一、审计合规要点

1. **快照字段**：`hr_employee` 和薪资记录中的 `post_level`、`org_name`、`employee_name` 等冗余字段写入时固化，禁止关联查询实时值，保证历史可追溯。
2. **操作审计**：所有薪资修改、离职操作写 `sys_audit_log`（`oper_module=MODULE_HR_SALARY` / `MODULE_HR_TRANSFER`），记录操作人、操作时间、变更前值、变更后值。
3. **离职账号联动**：离职审批通过后必须禁用关联系统账号，禁止仅修改员工状态而不处理账号。
4. **薪资数据不可逆**：薪资核算单一旦发放（`pay_status=1`），禁止修改，只能冲红生成反向计划。
5. **敏感权限操作**：`hr:salary:archive:edit`（薪资档案修改）、`hr:resign:add`（离职申请）、`hr:salary:month:pay`（薪资发放）操作后必须写审计日志。

## 十三、注意事项

1. **companyId 必传**：所有 HR 业务操作的请求参数中必须携带 `companyId`，由前端从 `userStore.userInfo?.companyId` 获取，**不可从 URL 参数推测**，后端不信任前端传入的 `company_id`。
2. **userStore 属性名**：用户信息存储在 `userStore.userInfo`（非 `userStore.user`），包含 `id`、`companyId`、`username`、`realName` 等字段。
3. **快照字段原则**：`employee_name`、`org_name`、`post_level` 等展示字段在创建时写入快照，后续源数据变更不影响历史快照数据。
4. **int 常量比较**：`CommonConst` 中定义的 int 类型常量（如 `APPLY_STATUS_DRAFT = 0`）不可使用 `.equals()` 方法比较，必须使用 `Objects.equals()` 或 `==` 运算符。
5. **敏感信息加密**：`id_card_no`、`phone`、`bank_account` 字段在数据库存储 AES 密文，VO 层统一脱敏返回（身份证：`410*******1234`，手机号：`138****1234`）。
6. **流程定义编码**：所有流程提交统一使用 `CommonConst.FLOW_DEF_HR_*` 常量，禁止在业务代码中硬编码字符串。
7. **权限常量**：所有权限标识统一使用 `PermissionConst.HR_*` 常量，禁止硬编码权限字符串。
8. **离职流程**：离职审批通过后，必须通过 `SysUserService.disableUser()` 禁用关联的 `sys_user` 账号，禁止仅修改 `hr_employee.employee_status` 而不处理账号。
9. **薪资档案修改**：薪资档案修改属于敏感操作，必须写 `sys_audit_log`（`oper_module=MODULE_HR_SALARY`），记录变更前后金额。

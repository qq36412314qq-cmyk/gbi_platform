# 加班管理模块设计方案 v1.0

## 一、方案概述

### 1.1 背景
当前系统已具备考勤记录（`hr_attendance_record`）、员工班次（`hr_employee_shift`）、请假记录（`hr_leave_record`）和月度薪资核算（`hr_salary_month`）等模块，但缺少加班管理的完整功能。本方案设计加班申请、加班记录、加班补偿和加班薪酬计算等核心功能，与现有考勤、薪资模块无缝对接。

> **与企微集成定位**：企业微信作为加班申请的数据采集入口（员工通过企微提交加班申请），本系统作为加班数据的处理和核算中心。两者职责清晰分离，互不替代。

### 1.2 设计目标
1. 实现加班申请审批流程
2. 自动识别加班时长（基于打卡记录）
3. 支持调休和加班费两种补偿方式
4. 加班数据自动接入月度薪资核算
5. 符合《薪酬核算考勤联动规范》的计算逻辑

### 1.3 适用场景
| 场景 | 说明 |
|------|------|
| 标准工时制 | 工作日加班1.5倍，休息日加班2倍，法定节假日加班3倍 |
| 综合工时制 | 周期内总工时超过法定标准部分按1.5倍计算 |
| 不定时工时制 | 不计算加班，仅记录备案 |
| 调休优先 | 加班优先安排调休，未休完部分发放加班费 |

### 2.2 业务流程

#### 2.2.1 加班申请流程
```
员工提交申请（企微表单或系统Web端） → 主管审批 → 审批通过 → 生成加班记录 → 月末结算
     ↓                    ↓              ↓
   撤回/驳回            转交/加签     调休/加班费选择
     ↓                    ↓              ↓
  [企微侧] 员工可在企微查看审批进度  [系统侧] 推送审批结果消息到企微
```

#### 2.2.2 自动识别加班流程
```
每日22:00定时任务
    ↓
扫描当日考勤记录
    ↓
判断下班时间 > 班次结束时间
    ↓
过滤请假/出差人员
    ↓
生成待确认加班记录
    ↓
员工确认 → 主管审核 → 归档
```

#### 2.2.3 加班补偿流程
```
月末汇总加班记录
    ↓
判断补偿方式（调休/加班费）
    ↓
调休：生成调休额度 → 员工申请调休 → 主管审批 → 抵扣加班时长
    ↓
加班费：计入月度薪资 → 参与薪资核算 → 发放
```

#### 2.2.4 企业微信集成流程

##### 2.2.4.1 加班申请提交（企微侧 → 系统侧）
```
员工在企微应用「GBI审批」中选择「加班申请」表单
    ↓
填写：加班日期、开始/结束时间、事由、补偿方式
    ↓
企微表单提交 → 企微API调用系统回调接口 / 表单结果通过审批流回写系统
    ↓
系统在 hr_overtime_apply 表创建申请记录（status=0 待审批）
    ↓
系统通过企微消息接口推送：「您有一条新的加班申请，请及时审批」给主管
```

##### 2.2.4.2 审批结果回调（企微侧 → 系统侧）
```
主管在企微中点击「同意/拒绝」
    ↓
企微审批回调接口：POST /api/wecom/callback?agent-id={AgentId}
    ↓
WecomCallbackController 解析审批事件，提取:
  - 审批实例ID（flow_instance_id）
  - 审批结果（通过/驳回）
  - 审批人ID
  - 审批时间
    ↓
调用 HrOvertimeApplyService.updateApprovalResult()
  - 更新 hr_overtime_apply.status（1已通过/2已驳回）
  - 更新 approve_time、approve_by、approve_opinion
  - 审批通过后：生成待确认加班记录（hr_overtime_record）
  - 记录审批日志 + wecom_message_record
```

##### 2.2.4.3 加班确认通知（系统侧 → 企微侧）
```
系统自动识别或员工手动确认加班记录
    ↓
判断是否需要确认（status=0 待确认）
    ↓
通过 WecomMessageService 发送卡片消息给员工:
  - 标题：「加班记录待确认」
  - 内容：日期、时段、时长、类型
  - 按钮：「确认」/「申诉」
    ↓
员工点击「确认」→ 企微回调确认接口
    ↓
系统更新记录状态为「已确认」
```

##### 2.2.4.4 补偿结果通知（系统侧 → 企微侧）
```
月末补偿结算完成
    ↓
循环每个员工：
  - 调休：推送「本月调休额度 XX 小时，可申请使用」
  - 加班费：推送「本月加班费 ¥XXX 已计入薪资」
    ↓
通过 WecomMessageService 发送文本/卡片消息
    ↓
写入 wecom_message_record 表记录发送结果
```

## 四、核心业务逻辑设计

### 4.1 加班时长计算规则

#### 4.1.1 工作日加班
```
加班时长 = 下班打卡时间 - 班次结束时间
限制：最长不超过24小时
扣除：用餐时间30分钟（如配置）
```

#### 4.1.2 休息日/法定节假日加班
```
加班时长 = 下班打卡时间 - 上班打卡时间
无用餐时间扣除
```

#### 4.1.3 时长取整规则
| 取整模式 | 示例 | 说明 |
|---------|------|------|
| 向上取整 | 1.1小时 → 2小时 | 不满1小时按1小时计 |
| 四舍五入 | 1.4小时 → 1小时 | 0.5以下舍去 |
| 向下取整 | 1.9小时 → 1小时 | 不满整小时部分舍去 |

### 4.2 加班费计算公式

```
日薪 = basicSalary / 21.75
时薪 = 日薪 / 8

工作日加班费 = 时薪 × 加班时长 × 1.5
休息日加班费 = 时薪 × 加班时长 × 2.0
法定节假日加班费 = 时薪 × 加班时长 × 3.0

加班费合计 = Σ(各类型加班费)
```

### 4.3 调休抵扣规则

```
调休额度 = 加班时长 × 补偿系数（默认1.0）
可调休时长 ≤ 加班时长
调休申请成功后，对应加班记录标记为"已抵扣"
```

### 4.4 自动识别逻辑

```java
// 伪代码
for each attendance_record in today:
    if employee.exemptAttendance == 1:
        continue  // 免考勤员工跳过
    
    if attendance_record.clockOutTime > shift.shiftEndTime:

```

## 十五、企业微信集成设计

### 15.1 集成能力总览

| 功能 | 方向 | 触发条件 | 技术实现 |
|------|------|----------|----------|
| 加班申请提交 | 企微→系统 | 员工在企微表单提交 | 企微审批API回调（或Webhook） |
| 审批待办通知 | 系统→企微 | 新申请进入审批流 | WecomMessageService.sendApprovalTodo() |
| 审批结果通知 | 系统→企微 | 审批流完成 | WecomMessageService.sendApprovalResult() |
| 加班记录确认 | 双向 | 自动识别或手动 | 卡片消息确认，企微回调更新状态 |
| 补偿结果通知 | 系统→企微 | 月末结算完成 | WecomMessageService.sendOvertimeCompensate() |
| 加班超时预警 | 系统→企微 | 累计超上限 | WecomMessageService.sendOvertimeWarning() |

### 15.2 企微侧配置

#### 15.2.1 应用配置
- 使用已有的「GBI审批」应用，无需单独创建加班应用
- 在「审批」模块中添加「加班申请」表单模板
- 表单字段与 `hr_overtime_apply` 表对应：日期、开始/结束时间、事由、补偿方式

#### 15.2.2 回调配置
- 回调URL：复用系统统一回调接口 `/api/wecom/callback`
- 监听事件类型：`approval_change`（审批状态变更）
- 通过 `flow_instance_id` 关联系统内的加班申请记录

#### 15.2.3 权限配置
- 需要 `审批流程读取` 权限（接收审批回调）
- 需要 `消息推送` 权限（发送通知）

### 15.3 系统侧接口

#### 15.3.1 回调处理接口
```
POST /api/wecom/callback?agent-id={AgentId}
  → 解析 approval_change 事件
  → 提取 flow_instance_id
  → HrOvertimeApplyService.updateApprovalResult()
```

#### 15.3.2 消息发送接口
```
WecomMessageService:
  - sendOvertimeApprovalTodo(employeeId, applicantName, date, hours)
      // 新加班申请提醒主管
  - sendOvertimeApprovalResult(employeeId, result, reason)
      // 审批通过/驳回通知员工
  - sendOvertimeConfirm(employeeId, date, hours, type)
      // 待确认加班记录通知
  - sendOvertimeCompensate(employeeId, month, totalHours, compensateType, amount)
      // 补偿结果通知
  - sendOvertimeWarning(employeeId, month, totalHours, limit)
      // 累计超上限预警
```

### 15.4 数据流向图

```
┌─────────────────────────────────────────────────────────────┐
│  加班申请全生命周期数据流                                  │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   企微表单提交 ──────────────────────────→ hr_overtime_apply │
│        （status=0）                                    (status=0) │
│                                                             │
│   企微审批回调 ──────────────────────────→ hr_overtime_apply │
│        （approval_change）                         (status=1)   │
│                                                             │
│   审批通过后 ──→ 自动生成 hr_overtime_record               │
│                              (status=0 待确认)              │
│                                                             │
│   企微卡片确认 ───────────────────────────→ hr_overtime_record│
│        （员工点击确认）                              (status=1)   │
│                                                             │
│   月末结算 ──→ 补偿核算 ──→ hr_salary_month                │
│                              （计入薪资）                   │
│                                                             │
│   各节点均有企微消息推送（wecom_message_record记录）        │
└─────────────────────────────────────────────────────────────┘
```

### 15.5 降级策略

**场景**：企微服务不可用或接口超时

| 场景 | 降级方案 |
|------|----------|
| 申请提交失败 | 员工可通过系统Web端手动提交，不受影响 |
| 审批回调延迟 | 支持手动在Web端输入审批结果，人工补充 |
| 消息推送失败 | 重试3次（指数退避），仍失败记录到日志，管理员可手动补发 |
| 企微整体宕机 | 不影响核心业务流，加班申请/审批/核算均在系统内正常进行 |

> **核心原则**：企微是增强通道，不是业务依赖。加班核心功能完全可以在系统Web端独立运行，企微仅作为便捷入口和通知渠道。

### 15.6 开发计划补充

在原有 6 个阶段基础上，增加企微集成的工作量：

| 阶段 | 新增内容 | 增量工期 |

| Phase 3 | 加班确认通知，调用 WecomMessageService | +0.5天 |
| Phase 4 | 补偿结果推送，月末结算后批量发送 | +0.5天 |
| Phase 6 | 联调测试企微全流程 | +0.5天 |

INSERT INTO sys_role_menu_rel (role_id, menu_id)

  AND permission NOT LIKE '%:delete%'

### 17.8 注意事项

1. **菜单ID**：SQL 使用 `LAST_INSERT_ID()` 动态取值，避免ID冲突；实际执行前需确认当前 `MAX(id)=232`
2. **Tab 模式 vs 独立页面**：当前建议独立子页面形式（`apply.vue/record.vue/compensate.vue/config.vue`），便于单独访问和路由跳转；后续如需聚合为单页Tab可调整
3. **角色授权**：新增菜单默认对 `role_id=4`（子公司经理）授予查看权限，`delete/revoke/pay/reject` 等敏感操作按钮不授权
4. **权限回退**：上线前需在「角色管理」页面逐项确认菜单权限分配是否符合预期

## 五、审批提交流程提示规范

> 适用场景：所有会触发后端自动业务逻辑的审批表单，提交前向用户展示提示信息，避免用户对后续系统自动操作无感知。

### 5\.1 适用审批类型

|审批类型|审批通过后自动化动作|提示时机|
|---|---|---|
|入职申请|创建员工档案 \+ 创建初始薪资档案V1|提交按钮上方|
|转正申请|更新员工状态为正式员工，生成新版本薪资档案V2|提交按钮上方|
|调岗申请|更新员工组织、岗位，生成新版本薪资档案|提交按钮上方|
|离职申请|更新员工为已离职，冻结薪资档案|提交按钮上方|
|薪资档案变更审批|旧版本失效，新版本激活生效|提交按钮上方|
|批量调薪审批|批量生成薪资档案新版本|提交按钮上方|
|补调薪申请|生成补差记录，随下月薪资发放|提交按钮上方|

### 5\.2 实现规范

1. 使用 `el‑alert` 组件放置于表单提交按钮上方；

2. 普通告知使用 `type="info"`；离职等不可逆风险场景使用 `type="warning"`；

3. 文案全部使用业务语言，**禁止直接展示数据库字段名（isCurrent、version\_no等）**；

4. 提示仅做告知，不阻塞表单提交；

5. 提示文案必须和后端实际执行逻辑严格对齐。


### 5\.4 业务提示文案参考

**入职申请**

> 即将提交入职申请，审批通过后系统将自动：
• 创建员工档案（基本信息、工作经历、学业经历）
• 创建初始薪资档案V1版本
• 【可选】自动创建系统登录账号

**转正申请**

> 即将提交转正申请，审批通过后系统将自动：
• 更新员工状态为“正式员工”
• 创建新薪资档案版本V2

**调岗申请**

> 即将提交调岗申请，审批通过后系统将自动：
• 更新员工组织架构与岗位信息
• 创建新版本薪资档案

**离职申请（warning）**

> ⚠️ 即将提交离职申请，审批通过后系统将自动：
• 更新员工状态为“已离职”
• 冻结薪资档案，不再参与薪资核算
• 员工将无法访问业务系统，请确认信息无误再提交

**薪资档案变更**

> 提交薪资档案变更，审批通过后：旧薪资档案转为历史版本，新版本正式生效。

**补调薪申请**

> 提交补调薪申请，审批通过生成补差记录，差额将跟随下个月薪资发放；不会修改历史已核算薪资数据。

## 第十章、补调薪（追溯发放）机制设计

### 10\.1 问题场景

> 场景：员工 A 于 2026‑07‑01 入职，薪资档案于 2026‑07‑01 生效（V1）。
2026‑08‑15 员工调薪至新标准（V2），但当时忘记提交审批。
2026‑09‑01 才发现，此时 8 月份薪资已按 V1 核算完毕。
问题：如何弥补 8 月份少发的薪资差额？

### 10\.1\.2 核心设计思路：**补调薪不修改历史数据，只创建补差记录**


### 10\.3 补调薪与月度薪资联动

## 第十一章、薪资档案自动生成专项实现细则

> 本章解决：入职/转正自动生成薪资档案、员工档案与薪资链路打通、cityCode城市字段改造、月度薪资空值保护。

### 11\.1 当前业务痛点

1. 入职申请审批通过后，**仅创建员工档案，不会自动生成薪资档案**；月度薪资核算直接跳过该员工；

2. 转正审批通过，没有自动生成新版本薪资档案；

3. 入职申请缺少`cityCode`，社保公积金核算无法匹配城市费率；

4. 薪资档案版本控制逻辑缺失，切换生效缺少乐观锁并发保护；

5. 月度薪资生成没有“无薪资档案员工拦截告警”。

### 11\.4 转正 / 调岗 / 离职审批回调业务逻辑

1. **转正审批回调**

- 修改员工状态为正式员工；

- 创建新版本薪资档案V2；

- 提交薪资档案审批流。

2. **调岗审批回调**

- 更新员工`org_id`、`post_id`；

- 根据新岗位匹配薪资规则，生成新版本薪资档案；

- 提交薪资档案审批流。

3. **离职审批回调**

- 修改员工状态为已离职；

- 将该员工全部薪资档案置为历史版本，`is_current=0`，不再参与月度薪资核算。

> 重要：以上全部逻辑写在**FlowEngineService审批回调方法内，增加事务，异常捕获，记录业务告警日志**。

### 11\.5 薪资档案版本激活规则

1. 薪资档案审批通过回调：

    - 查询该员工全部生效档案，设置`is_current=0`；

    - 将本次审批通过档案设置`is_current=1`；

    - 使用**乐观锁version**做并发控制，防止多线程同时修改；

    - 更新`hr_employee.current_salary_archive_id`指向新档案ID。

### 11\.6 月度薪资生成空值保护伪代码

```Java
/**
 * 生成月度薪资前校验：在职员工必须拥有生效薪资档案
 */
@Override
public void generateMonth(SalaryMonthDTO dto) {
    // 1.查询当前租户 is_current=1的薪资档案员工ID集合
    List<Long> hasSalaryEmpIds = salaryArchiveMapper.selectList(
        new LambdaQueryWrapper<HrSalaryArchive>()
                .eq(HrSalaryArchive::getCompanyId, loginUser.getCompanyId())
                .eq(HrSalaryArchive::getIsCurrent, 1)
                .select(HrSalaryArchive::getEmployeeId)
    ).stream().map(HrSalaryArchive::getEmployeeId).collect(Collectors.toList());

    // 2.查询在职、试用期员工
    List<HrEmployee> allOnJobEmp = employeeMapper.selectList(
            new LambdaQueryWrapper<HrEmployee>()
                    .eq(HrEmployee::getCompanyId, loginUser.getCompanyId())
                    .in(HrEmployee::getEmployeeStatus, 1,2)
    );

    // 3.找出缺少薪资档案的员工
    List<String> noSalaryEmpNames = allOnJobEmp.stream()
            .filter(e -> !hasSalaryEmpIds.contains(e.getId()))
            .map(HrEmployee::getName)
            .collect(Collectors.toList());

    if(!CollectionUtils.isEmpty(noSalaryEmpNames)){
        log.warn("生成月度薪资，发现{}名在职员工无生效薪资档案：{}",noSalaryEmpNames.size(),noSalaryEmpNames);
        throw new BizException("以下员工缺少生效薪资档案，请先维护薪资档案："+ String.join("，",noSalaryEmpNames));
    }
    // 继续执行原有薪资生成逻辑
}
```

5. **并发安全**：薪资档案切换生效，必须使用数据库乐观锁version字段。

## 十二、生产实操场景完善与容错兜底优化（补充增强）

本章节基于真实业务实操场景，针对方案原有理想正向流程，补充**异常边界、回调容错、数据兜底、重复提交拦截、存量数据兼容、前端交互优化、权限审计加固**等生产级能力，解决系统上线后核心业务断裂、数据错乱、无法兜底修复的问题，所有优化内容均贴合现有业务架构，不改动原有核心流程，仅做增强完善，同时覆盖多场景实操约束、异常处理、运维补偿、财务对账等落地必备能力。结合全场景实操复盘，对各业务模块补充完整落地约束与容错逻辑，补齐方案原有缺失的生产级细节。

### 12\.1 审批回调核心容错机制（最高优先级生产加固）

方案原有设计仅覆盖审批回调成功的正向流程，缺失回调超时、网络异常、消息丢失、重复回调、业务执行失败等异常场景，极易出现「审批已通过、业务数据未生成」的数据断裂问题，现补充完整容错与补偿体系，适配**入职、转正、调岗、离职、薪资档案、批量调薪、补调薪**所有审批类单据，实现生产环境稳定运行与异常可排查、可修复，同时补充幂等性、事务兜底、告警机制，彻底解决审批回调业务数据不一致问题。

#### 12\.1\.1 业务执行状态字段扩展

所有审批业务申请表（入职、转正、调岗、离职、薪资档案、批量调薪、补调薪）统一新增3个兜底字段，用于标记审批后业务执行状态，精准区分待执行、执行成功、执行失败场景，支撑异常排查、数据对账与手动补偿，彻底解决生产环境业务数据静默异常、无日志可查、无法修复的问题。

```SQL
-- 通用审批业务执行兜底字段（全审批单据统一新增）
exec_status TINYINT DEFAULT 0 COMMENT '审批后业务执行状态：0待执行 1执行成功 2执行失败',
exec_msg VARCHAR(1000) COMMENT '业务执行异常信息，用于异常排查',
exec_time DATETIME COMMENT '业务实际执行完成时间';
```

#### 12\.1\.2 审批回调核心业务约束（幂等\+事务\+告警）

1\. 幂等校验：所有审批回调执行业务逻辑前，优先判断单据exec\_status状态，若为1（执行成功），直接返回，禁止重复执行业务，杜绝重复创建员工档案、薪资档案、补差记录等数据错乱问题；

2\. 事务兜底：所有审批后置业务逻辑全部包裹独立事务，业务异常全程try\-catch捕获，异常后自动更新exec\_status=2、记录exec\_msg异常详情、更新exec\_time，**禁止向上抛出异常阻断工作流引擎**，避免流程死循环重试；

3\. 异常告警：当exec\_status更新为2时，系统输出ERROR级别日志，可对接钉钉/企业微信告警，实时推送异常单据信息、错误原因，便于运维及时处理；

4\. 手动补偿能力：新增运维专属【审批业务异常补偿页面】，仅后台运维权限可见，展示所有exec\_status≠1的异常单据（含单据类型、ID、异常信息、提交人、时间），提供**手动重试执行**功能，实现异常业务一键兜底修复。

#### 12\.1\.3 重复回调拦截规则

针对工作流引擎重复投递回调场景，增加全局拦截逻辑：同一流程实例ID、同一单据ID，10秒内重复回调直接拦截，结合exec\_status幂等判断，双重保障无重复业务执行。

### 12\.2 入职申请模块实操场景完善

补充方案缺失的驳回重提、文件垃圾清理、JSON数据容错、账号创建兜底等真实场景逻辑：

1\. 驳回重提防重复建档：hr\_entry\_apply新增exec\_biz\_id字段，用于存储审批通过后生成的员工ID，驳回修改重新提交审批通过后，判断字段是否存在，已存在则不再重复创建员工档案、薪资档案，彻底解决重复建档问题；

2\. 系统账号创建容错：自动创建系统账号为附属功能，账号重复、手机号冲突、创建异常时，仅记录日志并告警，**不阻断员工档案、薪资档案主流程生成**，exec\_status仍标记为执行成功，避免核心业务中断；

3\. 照片文件垃圾清理：用户多次编辑草稿、替换照片时，旧的photo\_file\_id标记为待回收，系统定时任务自动清理未被任何业务单据引用的废弃文件，减少服务器文件冗余；

4\. 经历JSON数据容错：前端提交表单时强制校验工作、学业经历JSON合法性；后端解析JSON增加try\-catch容错，解析失败则标记exec\_status=2、记录异常，进入补偿重试页面；正式员工经历数据严格落实体子表，JSON仅作为申请单临时存储，不依赖JSON生成正式档案。

### 12\.3 薪资档案模块实操场景完善

补充方案缺失的存量数据、驳回逻辑、离职约束、特殊人员适配等核心场景：

1\. 存量历史数据兼容：系统上线前存量在职老员工无薪资档案，新增【存量员工薪资档案批量初始化】后台功能，支持批量导入老员工薪资档案；同时新增薪资校验空值保护开关，上线迁移阶段可临时关闭校验，迁移完成后强制开启，避免初期薪资核算全员报错、业务停摆；

2\. 审批驳回业务规则：薪资档案审批驳回后，新版本记录保留且is\_current=0，不覆盖、不替换原有生效版本，仅标记为作废草稿，保证历史生效薪资档案不受影响；

3\. 离职人员约束：员工状态为已离职时，系统拦截所有新增、编辑、提交薪资档案版本的操作，禁止离职员工更新薪资配置；

4\. 特殊人员适配：适配外包、临时人员场景，通过入职申请auto\_create\_salary\_archive开关控制，关闭后自动跳过薪资档案创建，员工标记为【无需建档】，月度薪资核算自动过滤该类人员，不产生校验拦截报错。

### 12\.4 补调薪模块实操场景完善

补齐财务对账、离职兜底、时间边界、重复申请约束等实操缺失逻辑：

1\. 业务边界拦截：已离职员工禁止提交补调薪申请；追溯月份仅支持历史月份，禁止选择当前及未来月份，避免无效数据生成；

2\. 重复申请规则：同一员工、同一追溯月份，支持多条补调薪记录，所有差额自动合并至下月薪资统一发放，记录独立留存、可单独溯源；

3\. 财务对账优化：hr\_salary\_month新增salary\_type字段（1正常薪资 2含补差薪资），薪资明细导出区分正常工资金额、补差金额；补调薪明细表新增财务备注、凭证号字段，支撑财务凭证对账、归档；

4\. 离职补差兜底：补调薪生成后未发放、员工中途离职的场景，系统不丢弃未发放补差，新增独立【未发放补差手动发放】页面，支持财务单独发放，保障员工薪资权益、财务数据完整。

### 12\.5 全流程申请单重复提交拦截

统一约束全品类员工申请单，规避并行审批、数据错乱问题：同一员工，同一类型申请（转正、调岗、离职、薪资变更、补调薪），系统仅允许存在**一条草稿/审批中**状态单据，重复点击新增时弹窗拦截提示，避免多条并行审批单导致的数据覆盖、重复执行问题。

### 12\.6 跨流程业务联动约束

1\. 调岗联动规则：员工调岗审批过程中，存在未审批完成的转正、薪资变更申请时，调岗审批通过后，自动作废原有待审批单据，弹窗提示用户重新提交，避免岗位信息与薪资、员工状态不匹配；

2\. 离职联动规则：员工提交离职申请后，系统自动作废所有待审批、审批中的转正、调岗、薪资变更单据，同步记录审计日志，保证离职员工数据状态统一；同时弹窗提示HR该员工是否存在未发放补差、未完结考勤异常，提前校验兜底。

### 12\.7 月度薪资核算实操优化

补齐月份边界、事务粒度、数据锁防护逻辑：

1\. 入职/离职当月计薪：补充明确业务规则，支持适配当月入职、当月离职员工的按天计薪核算逻辑，纳入月度薪资统一计算；

2\. 事务粒度优化：月度薪资核算采用**单员工独立事务**，单个员工核算失败仅标记自身异常、记录日志，不影响其他员工薪资生成，避免全局事务回滚导致全员薪资生成失败；

3\. 薪资数据锁防护：月度薪资经财务审核发放后，自动添加状态锁，pay\_status≠0时，禁止重复生成、覆盖、修改历史薪资数据，保证已发放薪资数据不可篡改，符合财务合规要求。

### 12\.8 前端交互实操优化

修复现有前端交互遗留问题，统一用户体验，消除残留异常：

1\. 弹窗表单重置：所有新增/编辑审批弹窗关闭后，强制执行表单校验重置（formRef\.clearValidate\(\)），杜绝二次打开弹窗残留上次红色校验提示的问题；

2\. 差异化提示文案：区分「新增申请」和「驳回重提」场景的el\-alert提示文案，驳回编辑场景明确提示“修改后重新提交，审批通过后将自动更新相关业务数据”，文案与后端逻辑严格对齐；

3\. 异常状态醒目展示：所有审批详情页醒目展示exec\_status执行状态，若审批通过但业务执行失败，高亮警告提示异常信息，支持直接跳转补偿修复页面。

### 12\.9 权限与数据安全加固

补齐方案缺失的数据权限、敏感数据防护能力：

1\. 数据权限规则：新增HR模块数据权限约束，各级HR仅可查看、操作自身管辖组织下的所有员工申请单、薪资、考勤数据，杜绝跨组织数据查看；

2\. 敏感数据防护：薪资档案、月度薪资、补差明细等敏感数据，禁止纳入普通申请单导出接口，单独薪资导出功能配置独立权限标识，无权限用户无法查看、导出薪资敏感数据。

### 12\.10 审计日志完善规范

统一补充全场景审计日志，满足运维排查、合规追溯需求：

1\. 所有审批回调业务执行（成功/失败）强制记录审计日志，包含单据ID、执行结果、异常信息、执行时间；

2\. 运维手动补偿重试操作，全程记录操作人、操作时间、重试单据、执行结果；

3\. 薪资档案变更、批量调薪、补调薪操作，完整记录变更前后薪资明细、差额、操作原因，实现薪资数据全链路可追溯。

### 12\.11 上线必测核心用例（补充落地校验标准）

新增系统上线前必须覆盖的异常测试用例，保障所有容错逻辑生效：

1\. 审批回调超时、异常失败，验证手动补偿重试功能可用性；

2\. 单据驳回后重新提交，验证无重复建档、无重复薪资生成；

3\. 存量无薪资档案员工批量初始化、校验拦截功能正常生效；

4\. 离职员工拦截补调薪、薪资新增操作验证；

5\. 薪资档案驳回不覆盖旧生效版本验证；

6\. 重复回调幂等性、无重复执行业务验证；

7\. 特殊人员关闭自动建档后，不参与薪资核算校验验证；

8\. 员工离职后未发放补差独立发放、数据不丢失验证。

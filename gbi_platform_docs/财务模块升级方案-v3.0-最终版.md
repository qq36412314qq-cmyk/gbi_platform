### 1.3 核心问题清单

| 问题类别 | 具体问题 | 影响 |
|----------|----------|------|
| **无聚合支付载体** | biz_fee_bill 按单一规则生成，无法一次支付多个收费项目 | 用户需多次支付，体验差 |
| **缴费粒度错配** | 财务流水关联单条 biz_fee_bill.id | 合并支付时无法体现"一次支付"语义 |
| **缺少缴费单编号** | 前端无统一缴费凭证展示 | 用户无法感知"我缴了一张单" |

| **快照字段缺失** | BizFinanceFlow 实体缺少 pay_bill_id/pay_bill_no 字段 | 财务流水无法关联缴费单 |
| **DTO 兼容性不足** | UnifiedPayDTO 只有 billId，不支持 payBillId | 无法支持缴费单聚合支付 |
| **flow_status 异常** | 数据中存在 flow_status=6，超出定义范围(1-4) | 状态机不规范 |
| **前端视图不完整** | unpaidBill.vue 缺少合并缴费功能 | 用户无法批量缴费 |

## 二、设计方案

### 2.1 核心设计思想

**引入「缴费单」(biz_pay_bill) 作为聚合支付载体：**

- 一张缴费单 = 用户可以一次支付的对象
- 缴费单包含 N 条收费明细（biz_pay_bill_item）
- 缴费单级别的状态机：待缴 → 部分缴费 → 已缴 → 已退费/已冲红/已作废
- 财务流水关联缴费单（而非单条收费账单）

### 2.2 新增表结构

#### 表1：biz_pay_bill（缴费单主表）

```sql
DROP TABLE IF EXISTS `biz_pay_bill`;
CREATE TABLE `biz_pay_bill` (

  `company_id` bigint(20) NOT NULL DEFAULT 0 COMMENT '所属子公司ID',
  `pay_bill_no` varchar(64) NOT NULL COMMENT '缴费单编号（PY+公司编码+日期+序号）',
  `source_type` varchar(32) NOT NULL COMMENT '来源类型 contract=租赁合同 fee_bill=收费账单',
  `source_id` bigint(20) NOT NULL COMMENT '来源单据ID',
  `stall_id` bigint(20) NOT NULL COMMENT '铺位ID',
  `merchant_id` bigint(20) NULL DEFAULT NULL COMMENT '商户ID',
  `total_amount` decimal(12,2) NOT NULL DEFAULT 0.00 COMMENT '缴费单总金额',
  `paid_amount` decimal(12,2) NOT NULL DEFAULT 0.00 COMMENT '已缴金额',
  `unpaid_amount` decimal(12,2) NOT NULL DEFAULT 0.00 COMMENT '未缴金额',
  `pay_status` tinyint(4) NOT NULL DEFAULT 0 COMMENT '缴费状态 0待缴 1部分缴费 2已缴 3已退费 4已冲红 5已作废',
  `pay_time` datetime NULL DEFAULT NULL COMMENT '缴费完成时间',
  `remark` varchar(500) NULL DEFAULT NULL COMMENT '备注',
  `create_by` bigint(20) NOT NULL DEFAULT 0 COMMENT '创建人用户ID',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_by` bigint(20) NULL DEFAULT NULL COMMENT '更新人用户ID',
  `update_time` datetime NULL DEFAULT NULL ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  `is_delete` tinyint(4) NOT NULL DEFAULT 0 COMMENT '逻辑删除 0正常 1删除',
  PRIMARY KEY (`id`) USING BTREE,
  UNIQUE INDEX `uk_pay_bill_no`(`pay_bill_no` ASC, `is_delete` ASC) USING BTREE,
  INDEX `idx_company_id_is_delete`(`company_id` ASC, `is_delete` ASC) USING BTREE,
  INDEX `idx_stall_id`(`stall_id` ASC) USING BTREE,
  INDEX `idx_source`(`source_type` ASC, `source_id` ASC) USING BTREE
) ENGINE = InnoDB CHARACTER SET = utf8mb4 COLLATE = utf8mb4_0900_ai_ci COMMENT = '缴费单主表（聚合支付载体）' ROW_FORMAT = Dynamic;
```

### 2.4 状态机设计

#### biz_pay_bill 缴费单状态机

```
待缴(0) ──支付──► 部分缴费(1) ──支付──► 已缴(2)
                      │                       │
                      └──退费──► 已退费(3)     └──退费──► 已退费(3)
                        │
                        └──冲红──► 已冲红(4)
                      
待缴(0) ──作废──► 已作废(5)
```

**约束**：
- 仅待缴(0)状态可作废
- 已缴(2)状态可退费/冲红
- 已退费(3)/已冲红(4)/已作废(5)不可再次操作

#### biz_fee_bill 账单状态机（保持不变）

```
待缴(0) ──缴费──► 已缴(1)
           └──部分缴费──► 部分缴费(2)
```

#### biz_finance_flow 流水状态机（保持不变）

```
正常(1) ──冲红申请──► 冲红中(2) ──审批通过──► 已冲红(3)
                                      └──审批驳回──► 正常(1)
正常(1) ──作废──► 已作废(4)
```

#### 3.2.3 UnifiedPayDTO 兼容设计

```java
@Data
public class UnifiedPayDTO implements Serializable {
    /** 旧：biz_fee_bill.id */
    private Long billId;
    
    /** 新：biz_pay_bill.id（缴费单聚合支付） */
    private Long payBillId;
    
    /** 业务类型 */
    private String billType;
    
    /** 支付渠道 */
    private Integer payType;
    
    /** 幂等请求ID */
    private String requestId;
    
    /** 备注 */
    private String remark;

    /**
     * 解析目标ID：优先 payBillId，回退 billId
     */
    public Long resolveTargetId() {
        return payBillId != null ? payBillId : billId;
    }
}
```

### 3.3 关键设计决策说明

#### 决策1：缴费单不提前创建

**决策**：缴费单在用户点击合并缴费时动态聚合创建，而非合同签订时创建

**原因**：
1. 合同签订时可能只生成单条账单，用户可能只缴单条
2. 合并缴费是用户行为驱动的，不应预生成
3. 避免大量空缴费单占用数据空间
4. 缴费单是支付载体，不是业务单据

#### 决策2：保留 biz_fee_bill 独立存在

**决策**：不删除 biz_fee_bill，仅新增 pay_bill_id 关联字段

**原因**：
1. biz_fee_bill 是收费规则的产物，具有独立的业务语义
2. 历史数据兼容，存量 biz_fee_bill 无 pay_bill_id（NULL）
3. 单条缴费场景仍需 biz_fee_bill 作为载体
4. 双表并行保证平滑迁移

#### 决策3：财务流水关联缴费单而非账单

**决策**：biz_finance_flow.pay_bill_id 指向缴费单

**原因**：
1. 用户感知的是"我缴了一张单"而非"我缴了N条账单"
2. 聚合支付时，一条流水对应一个缴费动作
3. 便于对账，缴费单编号 = 用户凭证编号
4. 旧流水 pay_bill_id=NULL 过渡期兼容

## 十、验收标准

1. **新写入的物业流水**：stall_number, stall_name, stall_market_name, category_name, merchant_name 五个快照字段均有值
2. **新写入的非物业流水**：payer_name, payer_phone, payer_type, contract_no, contract_id 均有值
3. **历史流水查询**：显示的是交易发生时的名称，不受基础档案后续变更影响
4. **退费记录**：快照字段与原缴费记录一致
5. **押金流水**：物业押金（含铺位快照）和非物业押金（含缴费人快照）均正确写入
6. **导出 CSV**：包含全部快照字段和缴费单编号，数据与页面一致
7. **合并缴费**：勾选多条账单可生成一张缴费单，一条流水
8. **部分缴费**：缴费单支持多次部分缴费，状态正确流转
9. **冲红作废**：冲红/作废流程符合状态机约束
10. **编译通过**：无编译错误，服务启动无 WARN/ERROR

## 十一、附：与其他快照规范的统一性说明

| 表 | 快照字段 | 写入时机 | 约束 |
|---|---|---|---|
| `water_elec_bill` | category, unit_price | 账单生成时 | "规则修改不回溯" |
| `biz_discount_apply` | policy_snapshot | 优惠申请提交时 | "审批后计算依据，固化不回溯" |
| `biz_fee_bill_detail` | fee_item_name, calc_mode, price | 账单生成时 | 生成即锁定 |
| `biz_finance_flow` | 物业快照+非物业快照+缴费单快照 | 缴费/退费写入时 | "写入时固化，禁止修改" |
| `water_elec_pay_record` | 物业快照 | 缴费/退费写入时 | "写入时固化，禁止修改" |
| `biz_pay_bill_item` | rule_name, fee_item_name, bill_month | 缴费单创建时 | "生成即锁定" |

七张表的快照策略完全统一，符合《MySQL8.0数据库设计规范》中"关键业务数据写入时固化，禁止回溯变更"的审计要求。

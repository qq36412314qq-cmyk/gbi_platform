# 应收应付计划 + 统一审批引擎 + 优惠管理模块设计规范

## 文档描述

本规范为集团多业态一体化管控系统新增三大公共能力模块的设计标准，位于**财务账单之前的上游业务底座**：

1. **应收应付计划模块**（核心底座）：业务单据（租赁合同 / 报销单 / 采购单）自身审批通过后，自动生成应收 / 应付计划，账单、核销、经营流水统一依赖本表，实现"业务单据 → 应收应付计划 → 账单 → 收付款核销 → 财务流水"全链路数据同源；
2. **统一审批公共引擎**：同时承载"业务单据自身审批"（合同 / 报销 / 采购）与"敏感高危审批"（优惠超阈值、合同作废终止、计划大额调账），杜绝单人闭环操作，报销、采购后续直接复用；
3. **优惠管理模块**：免租期、折扣、减免策略化配置，租赁合同高频使用；报销 / 采购无优惠策略，仅做金额阈值校验；集团-子公司阈值管控，与合同、账单、财务流水自动联动。

配套两大财务专项能力（本规范一并设计）：

- **核销分摊明细（finance_writeoff）**：每笔资金主流水按 plan_id 精确分摊到应收应付计划，支持一流水核销多计划、退款 / 红冲负向冲减；
- **自动对账引擎**：以应收应付计划为权威源，`计划剩余 = plan总金额 − sum(有效核销分摊金额)`，与资金主流水自动核对，输出对账差异；单据作废 / 终止走**红冲链**（反向冲销计划 → 冲销账单 → 冲销核销 → 反向资金流水），全程审计可追溯。

本规范对齐《集团多业态一体化管控系统业务设计与全维度测试标准文档》《后端编码规范》《API & 日志规范》《MySQL8.0数据库设计规范》《权限 & 多租户隔离规范》《统一安全开发规范》全部条款，单人开发统一设计，后续实现代码、SQL 脚本、前端页面均以此为准。

> **与现有规范中 Flowable 的说明**：既有规范要求"统一 Flowable 流程引擎"，但当前工程（gbi_platform_server）尚未引入 Flowable 依赖，单人开发引入重引擎成本高。本设计采用**自研轻量表驱动审批引擎**（技术栈与现有 MyBatis-Plus、sys_permission_audit 二级复核一致），并抽象统一引擎接口，二期如需复杂工作流（会签/网关/超时自动流转）可平滑替换 Flowable，业务接入层不变。

# 一、模块定位与业务链路总览

## 1.1 业务链路全景（模块前置定位）

```
租赁合同 / 报销单 / 采购单（业务单据）
        │
        ▼
【业务单据自身审批】（合同审批 / 报销审批 / 采购审批，复用统一审批引擎）
        │
        ▼
【优惠策略管理】
    ├─ 租赁：免租期 / 折扣 / 减免
    └─ 报销 / 采购：优惠策略为空，仅做金额阈值校验
        │
        ├─ 优惠未超阈值 ───────────────────────┐
        └─ 优惠超阈值 ──▶ 【统一审批引擎】      │
                          │                    │
                          └── 审批通过 ──────────┘
                                    │
                                    ▼
                    【应收应付计划】计划生成（幂等）
                    规则：单据变更 → 旧计划作废，生成新计划；
                          重复回调不重复生成
                                    │
                                    ▼
                    【账单生成】（bill_plan_rel 中间表，支持多计划合并账单）
                    水电账单 / 收费规则账单（金额与计划同源校验）
                                    │
                                    ▼
                    【收付款核销】
                      ├─ 应收：租户缴费核销
                      └─ 应付：报销 / 采购付款核销
                          │（事务内：更新 plan 已付金额 + 写入资金主流水
                          │        + 写入核销分摊明细 finance_writeoff）
                          ▼
          finance_fee_pay_bill（全域资金主台账，标记 in/out 收支方向）
          finance_writeoff（核销分摊明细，每条绑定 plan_id）
                                    │
                                    ▼
        【自动对账引擎】
        以应收应付计划为权威源：
        计划剩余 = plan总金额 − sum(有效核销分摊金额)
        对比账面计划 & 核销流水，输出对账差异

        【作废 / 红冲分支】
        业务单据作废 / 终止 → 回调：旧计划作废 → 生成反向冲销计划
            → 冲销账单 → 冲销收付款核销 → 生成反向资金流水
```

## 1.2 模块职责边界

| 模块 | 职责 | 禁止行为 |
|---|---|---|
| 应收应付计划 | 记录"什么时间应收/应付谁多少钱"，全系统唯一应收应付台账；支撑账单、核销、对账 | 禁止直接修改已核销计划金额；禁止跨公司操作 |
| 统一审批引擎 | 业务单据自身审批 + 敏感业务审批（优惠超阈值、合同作废终止、计划调账、大额报销采购） | 禁止业务自建审批逻辑；禁止绕过引擎直接执行高危操作 |
| 优惠管理 | 优惠策略定义、优惠申请、阈值管控，优惠金额计算与快照 | 禁止脚本式公式；报销/采购不享受优惠策略 |
| 核销分摊 | 资金主流水与应收应付计划的精确对账关系 | 禁止无 plan_id 的孤儿核销；禁止跨公司分摊 |
| 自动对账引擎 | 以计划为权威源自动核对账面与流水，输出差异 | 禁止修改资金主流水、核销明细做假对账 |
| 红冲机制 | 单据作废/终止的负向冲销链，审计可追溯 | 禁止物理删除任何冲销链记录 |

## 1.3 一期 / 二期落地范围

| 迭代 | 内容 |
|---|---|
| 一期（本次设计落地） | 应收应付计划（合同生效自动生成收款计划 + 单据变更重建）、统一审批引擎（单据审批 + 合同优惠审批 + 合同作废终止审批 + 计划调账审批）、优惠管理（策略 + 申请 + 集团阈值）、核销分摊明细表、账单-计划中间表、基础自动对账（按计划汇总差异）、基础红冲链（作废终止 → 冲销计划 + 反向流水） |
| 二期 | 报销、采购单接入（金额阈值 → 大额流程审批 → 应付计划 direction=2 → 付款核销）；红冲链完善（冲账单 / 冲核销全链路页面）；对账引擎增强（定时任务 + 对账报表页）；计划逾期定时任务 |
| 三期 | 财务深度对接（金蝶凭证）、经营报表按计划维度出账 |

# 二、应收应付计划模块设计（核心底座）

## 2.1 业务定位

`finance_recv_pay_plan` 为全系统唯一应收应付台账表，替代业务各自零散记账：

1. **业务单据自动生成**：合同（单据审批通过后）自动生成押金与租金收款计划；二期报销 / 采购审批通过后生成付款计划（direction=2）；
2. **单据变更重建**：单据发生变更（如租金调整）→ 旧计划作废、按新金额生成新计划（版本可追溯）；重复回调不重复生成（幂等）；
3. **账单依赖底座**：账单生成通过 bill_plan_rel 中间表挂靠计划（支持多计划合并一张账单），金额与计划同源校验；
4. **核销依赖底座**：收付款核销在事务内"更新 plan 已付金额 + 写资金主流水 + 写核销分摊明细（finance_writeoff）"，每条核销绑定 plan_id；
5. **对账自动**：以计划为权威源，`计划剩余 = plan总金额 − sum(有效核销分摊金额)`，与财务流水按 plan_id 自动核对；
6. **作废 / 终止红冲**：业务单据作废 / 终止 → 旧计划作废 → 生成反向冲销计划 → 冲销账单 / 核销 → 生成反向资金流水，全程负向可追溯。

## 2.2 数据模型（finance_recv_pay_plan 应收应付计划主表）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|

| plan_no | varchar(64) | NOT NULL | 计划编号（生成规则见 2.4） |
| direction | tinyint | NOT NULL DEFAULT 1 | 方向：1应收 / 2应付（二期报销采购用） |
| biz_type | varchar(32) | NOT NULL | 业务类型：rent租金 / deposit押金 / property物业费 / fee_bill收费规则账单 / reimburse报销 / purchase采购 |
| source_type | varchar(32) | DEFAULT NULL | 来源单据类型：contract / reimburse / purchase / bill |
| source_id | varchar(128) | DEFAULT NULL | 来源单据 ID（合同 ID / 报销单 ID / 采购单 ID） |
| market_id | bigint | DEFAULT NULL | 市场 ID |
| stall_id | bigint | DEFAULT NULL | 铺位 ID |

| unpaid_amount | decimal(12,2) | NOT NULL DEFAULT 0.00 | 未收 / 未付金额 |

| overdue_days | int | NOT NULL DEFAULT 0 | 逾期天数（定时任务刷新） |
| flow_instance_id | bigint | DEFAULT NULL | 关联审批实例 ID（终止 / 作废 / 大额调账审批） |
| discount_apply_id | bigint | DEFAULT NULL | 关联优惠申请 ID |
| remark | varchar(500) | NULL | 备注（单据变更 / 红冲原因留痕） |
| 全局基础字段 | — | — | create_by / create_time / update_by / update_time / is_delete |

**索引**：

```sql
UNIQUE KEY uk_plan_no_company (plan_no, company_id, is_delete),
UNIQUE KEY uk_source_period (company_id, source_type, source_id, period_no, is_delete),
INDEX idx_company_id_is_delete (company_id, is_delete),
INDEX idx_due_date (due_date),
INDEX idx_stall_id (stall_id),
INDEX idx_orig_plan_id (orig_plan_id)
```

**核心业务约束**：

1. `uk_source_period` 保证同一来源单据同一期次唯一 → 计划生成**幂等**：重复回调直接跳过，不重复生成；
2. 金额公式：`plan_amount = original_amount − discount_amount + adjust_amount`，`unpaid_amount = plan_amount − paid_amount`；
3. 已发生核销的计划禁止直接修改金额，仅可通过**调账**（adjust_amount，写审计日志，超阈值走审批）或**单据变更重建**（旧计划作废 + 新计划）变更；
4. 计划仅逻辑删除；已核销计划、红冲计划、冲销链上任何记录禁止物理删除；
5. 红冲计划：red_flag=1、original_amount/plan_amount 为**负数**、orig_plan_id 指向被冲销计划，plan_status 按正常状态机流转（核销冲减后趋向完成）。

## 2.3 计划生成规则（租赁合同自动生成）

**触发时机**：合同单据审批通过且优惠审批通过（若超阈值）后，同一事务内调用 `RecvPayPlanService.generateByContract(contractId)`。

**生成内容**：

| 计划 | biz_type | period_type | period_no | due_date | original_amount |
|---|---|---|---|---|---|
| 押金 | deposit | 4一次性 | once | 合同生效日 | contract.deposit_amount |
| 租金（按月） | rent | 1按月 | 每月 yyyy-MM | 每月 1 日（或生效日所在月，按合同 start_time 对齐） | contract.rent_amount × 折扣率 |

**免租期处理**：合同免租期 waive_months=N 时，租赁期前 N 个月不生成租金计划（免租期月份不产生应收），从第 N+1 个月开始按月生成；减免金额（deduct_amount）按租赁期月数均摊冲减每月租金计划 original_amount。

**单据变更重建（版本化）**：合同租金 / 租期变更审批通过后：
1. 旧计划（未核销部分）置 plan_status=4 作废，remark 记录"被新计划 X 取代"；
2. 按新合同金额重新生成计划（orig_plan_id 指向旧计划）；
3. 已核销期次保留不动（历史账目不可改），仅未来期次重建；
4. 重复回调幂等：重建前按 `company_id + source_type + source_id + period_no` 查重，已存在直接跳过。

**生成后联动**：计划生成不写 finance_fee_pay_bill（流水仅在核销时写入），避免"应收 + 实收"双重复记账。

## 2.4 计划编号规则

`计划编号 = 方向 + 业务类型 + 公司 + 日期 + 序号`

- 应收租金：`AR-RENT-{companyId}-{yyyyMMdd}-{6位序号}`
- 应付报销（二期）：`AP-REIMB-{companyId}-{yyyyMMdd}-{6位序号}`
- 红冲计划沿用同规则，通过 red_flag=1 区分，不额外加后缀（序号保证唯一）。

## 2.5 收付款核销联动（事务边界：更新计划 + 主流水 + 分摊明细）

1. **核销入口**：应收侧租户缴费（复用现有幂等 requestId 机制）、应付侧报销 / 采购付款（二期）；
2. **事务内三写**（`@Transactional(rollbackFor = Exception.class)`）：
   - 更新计划 `paid_amount / unpaid_amount / plan_status`（0→1部分→2完成）；
   - 写入 finance_fee_pay_bill 资金主流水（新增 plan_id 列，flow_type=1 收入 / 2 支出）；
   - 写入 finance_writeoff 核销分摊明细（每条绑定 plan_id，writeoff_amount 正数）；
3. **一笔缴费核销多张计划**：前端勾选多张账单 / 计划 → 流水写一条（合并金额），分摊明细按计划各写一条（金额合计=流水金额），保证流水与分摊可核对；
4. **退款 / 红冲**：写负向核销分摊（writeoff_amount 负数，writeoff_type=2 退款 / 3 红冲），流水写支出方向（flow_type=2），计划 paid_amount 同步冲减；
5. **幂等**：requestId 唯一校验，重复回调不重复核销；核销完成后计划余额为 0 自动置 2 完成。

## 2.6 账单-计划关联（bill_plan_rel 中间表，支持多计划合并账单）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | bigint unsigned | PK | 主键 |
| company_id | bigint | NOT NULL | 所属子公司 ID |
| bill_type | varchar(32) | NOT NULL | 账单类型：water_elec / fee_bill |
| bill_id | bigint | NOT NULL | 账单 ID |
| plan_id | bigint | NOT NULL | 应收应付计划 ID |
| split_amount | decimal(12,2) | NOT NULL DEFAULT 0.00 | 该计划在本账单的分摊金额（账单总金额 = 各 rel 分摊合计，可含未挂计划的独立金额） |
| 全局基础字段 | — | — | 同上 |

```sql
UNIQUE KEY uk_bill_plan (bill_type, bill_id, plan_id, is_delete),
INDEX idx_company_id_is_delete (company_id, is_delete),
INDEX idx_plan_id (plan_id)
```

**生成规则**：

1. **收费规则账单（finance_fee_pay_bill）**：规则按周期先生成计划（biz_type=fee_bill）→ 账单金额源自计划，生成账单时按 bill_plan_rel 挂靠（同一铺位同周期多条计划可合并一张账单）；无计划（一次性杂费、无合同铺位）→ 账单独立存在（rel 为空）；
2. **水电账单（water_elec_bill）**：金额源自**抄表读数 × 单价**（非计划派生）→ 生成时若同铺位存在对应周期应收计划（如物业费计划 / 水电计划）则挂靠 rel 分摊关联；无计划则独立存在；
3. **金额校验**：账单挂靠计划时，账单金额与计划金额（或分摊部分）一致校验，不一致拒绝生成并提示；
4. **账单作废 / 红冲**：rel 记录同步逻辑删除标记，配合红冲链。

## 2.7 逾期、终止与红冲链

1. **逾期**：定时任务每日扫描 `due_date < 今天 AND unpaid_amount > 0 AND plan_status IN (0,1) AND red_flag=0` → 置 3 逾期，刷新 overdue_days，推送站内信 / 短信提醒（复用消息中台）；
2. **单据作废 / 终止红冲链**（合同退租 / 报销单作废等，审批通过后同一事务执行）：
   - ① 旧计划（未核销部分）置 plan_status=4 作废 / 5 终止，remark 记录红冲原因；
   - ② 生成反向冲销计划：red_flag=1、original_amount = −剩余未收金额、orig_plan_id = 旧计划 ID、due_date = 作废日；
   - ③ 冲销账单：关联未缴账单逻辑作废，bill_plan_rel 标记冲销；
   - ④ 冲销核销：旧计划已核销部分 → 写负向核销分摊（writeoff_type=3）+ 反向资金流水（flow_type=2，金额=已核销金额）；
   - ⑤ 冲销计划自身经核销（负向）后余额归零趋向完成，形成完整闭环；
3. **作废（误生成计划）**：plan_status=4，二次确认 + 审计日志；大额未收计划作废需走审批。

## 2.8 自动对账引擎

**对账口径**（以应收应付计划为权威源）：

```
计划剩余额 = plan_amount − SUM(finance_writeoff.writeoff_amount
             WHERE plan_id = 计划ID AND is_delete = 0 AND 有效核销)
```

- **有效核销**：writeoff_amount 含正数（核销入账）与负数（退款 / 红冲），按代数和参与计算；
- **对比项**：账面值（计划表 unpaid_amount）vs 计算值（上述公式），差异 ≠ 0 即对账异常；
- **流水核对**：资金主流水总额 vs 核销分摊合计（按 company_id / 时间范围），差异输出；
- **执行方式**：一期提供 `GET /finance/recvPayPlan/reconcile` 手动触发 + 分页展示差异；二期定时任务每日自动对账 + 对账报表页；
- **差异处理**：对账差异仅展示与告警（推送子公司管理员），不允许直接改流水 / 核销明细；排查后走调账或红冲修正。

# 三、统一审批引擎设计

## 3.1 设计原则

1. **一套引擎两类流程**：业务单据自身审批（contract / reimburse / purchase）+ 敏感高危审批（contract_discount / contract_terminate / plan_adjust / 大额单据），全部走本引擎，禁止业务自建审批逻辑（对齐《业务开发强制红线》第 1 条）；
2. **表驱动 + 配置化**：流程定义由集团配置（节点、审批人、抄送），子公司只读复用；大额场景通过"金额阈值动态选择大额流程定义"实现；
3. **状态机明确**：提交 → 审批中 → 通过 / 驳回 / 撤回 / 终止；
4. **业务回调解耦**：审批动作通过 `FlowBizHandler` 接口回调业务 Service，引擎不感知具体业务；
5. **与权限二级复核关系**：`sys_permission_audit`（权限类高危操作复核）一期保持独立，二期可迁移至本引擎统一待办；
6. **一期轻量引擎，二期可换 Flowable**：全部业务仅依赖 `FlowEngineService` 接口，替换实现不影响业务代码。

## 3.4 状态机与流转规则

```
草稿(业务侧) ──submit──▶ 审批中 ──最后一个节点pass──▶ 通过 ──▶ 业务回调 onPass
                           │  ▲
                           │  │ revoke（仅审批中可撤回，申请人）
                           ▼  │
                        撤回 ──▶ 业务回调 onCancel
审批中 ──任意节点reject──▶ 驳回 ──▶ 业务回调 onReject
审批中 ──transfer──▶ 原任务作废，转交人新增待办（保留父任务关联）
审批中 ──terminate（业务侧强制终止，如合同直接到期）──▶ 终止
```

1. **提交（submit）**：创建 flow_instance + 首节点 flow_task（按节点配置展开），写 flow_record；
2. **通过（pass）**：当前任务置已办；非最后节点 → 生成下一节点任务；最后节点 → 实例置通过，回调业务；
3. **驳回（reject）**：实例置驳回，所有剩余待办作废，回调业务；
4. **撤回（revoke）**：仅申请人可撤回审批中实例，回调业务；
5. **转交（transfer）**：原任务置已转交，新任务复制节点信息，targetHandler 处理；
6. **催办（urge）**：仅写 flow_record + 推送站内信，不改变流转。

## 3.5 业务接入规范（FlowBizHandler 回调接口）

```java
public interface FlowBizHandler {
    /** 支持的业务类型（如 contract / contract_terminate） */
    String bizType();
    /** 提交前业务校验（可选，如单据存在性、金额阈值） */
    default void onSubmit(Long sourceId) {}
    /** 审批通过回调（执行业务动作，如合同生效、优惠生效、计划生成、作废生效） */
    void onPass(Long sourceId, Long instanceId);
    /** 审批驳回回调（业务回滚草稿态） */
    void onReject(Long sourceId, Long instanceId);
    /** 撤回/终止回调 */
    default void onCancel(Long sourceId, Long instanceId) {}
}
```

**接入场景清单**：

| 流程编码 | 场景 | 触发条件 | 通过后业务动作 |
|---|---|---|---|
| contract | 合同自身审批 | 合同新建 / 变更，单据审批 | 进入优惠阈值判定；通过后合同生效 → 生成收款计划 |
| contract_discount | 租赁合同大额优惠 | 优惠申请超集团阈值（见第四章） | 合同优惠生效 → 计划按优惠快照生成 |
| contract_terminate | 合同作废 / 终止（退租） | 高危操作，一律必须审批 | 合同置已退租、铺位状态更新、执行红冲链 |
| plan_adjust | 计划大额调账 / 作废 | 单笔调账绝对值超集团阈值 | 应用调账金额，写审计日志 |
| reimburse / reimburse_large | 报销审批（二期） | 报销单提交；金额超阈值自动选 _large | 生成应付计划（direction=2） |
| purchase / purchase_large | 采购审批（二期） | 采购单提交；金额超阈值自动选 _large | 生成应付计划（direction=2） |

## 4.3 优惠计算规则

1. **免租期**：waive_months=N → 租赁期前 N 个月不生成租金计划，免租期折算优惠金额 = 月租金 × N × 折扣率；
2. **折扣率**：discount_rate=R% → 每月租金计划 original_amount = 合同月租金 × R%；
3. **减免金额**：deduct_amount=D → 按租赁期月数均摊，逐月冲减租金计划（第一期不足时并入最后一期）；
4. **组合**：先免租（当月不生成计划），再按折扣率折算，再扣减免，规则顺序固定；
5. **优惠总额** = 免租折算 + 原价 − 折扣后价 + 减免，优惠申请单快照存储，审批通过后不允许修改。

## 4.4 集团-子公司阈值管控（sys_config，集团全局 company_id=0，子公司只读）

| 参数 key | 默认值 | 说明 | 作用 |
|---|---|---|---|
| discount.waive_months_limit | 3 | 免租期上限（月） | 申请免租期超限 → need_audit=1 |
| discount.min_rate_limit | 80 | 折扣率下限（%） | 申请折扣低于下限 → need_audit=1 |
| discount.max_deduct_limit | 5000.00 | 单合同减免金额上限（元） | 申请减免超上限 → need_audit=1 |
| discount.contract_ratio_limit | 10.00 | 优惠占合同总租金比例上限（%） | 优惠总额占比超限 → need_audit=1 |
| plan.adjust_amount_limit | 2000.00 | 计划单笔调账阈值（元，绝对值） | 调账超阈值 → 必须走审批引擎 |
| plan.overdue_remind_days | 7 | 逾期提醒天数 | 逾期 N 天推送提醒 |
| reimburse.amount_limit | 5000.00 | 报销单金额阈值（元） | 报销金额超阈值 → 自动选用大额流程 |

**阈值判定流程（租赁）**：合同保存时计算优惠申请 → 任一指标超阈值 → need_audit=1 → 自动发起 contract_discount 流程实例 → 审批通过后合同才能生效；未超阈值 → 直接生效（普通优惠，单人可办，仍留审计）。

**金额阈值校验（报销 / 采购，二期）**：单据提交时金额超 reimburse.amount_limit / purchase.amount_limit → 自动选用 _large 大额流程定义（追加财务复核节点）→ 审批通过后生成应付计划。

## 4.5 与合同、账单联动

1. **合同**：合同表单选择优惠策略 → 生成优惠申请单（草稿）→ 阈值判定 → 审批 → 通过后合同生效；
2. **计划**：收款计划生成时读取优惠申请快照，original_amount 已含折扣折算，discount_amount 按快照分摊；
3. **账单**：收费规则账单 / 水电账单通过 bill_plan_rel 挂靠 plan_id，金额与计划同源；账单明细快照固化优惠后单价；
4. **流水**：缴费核销写 finance_fee_pay_bill 时 original_amount=原价、discount_amount=优惠分摊、real_amount=实收，与计划 plan_amount 一致对账；
5. **营销（二期）**：营销活动优惠复用 finance_discount_policy（discount_type 扩展），核销走同一套流水。

## 5.5 多租户约束

1. finance_recv_pay_plan / finance_writeoff / bill_plan_rel / finance_discount_apply / flow_instance / flow_task / flow_record 全部带 company_id，走 MyBatis-Plus 拦截器自动过滤；

## 5.6 审计与安全约束

1. 审计日志：计划生成 / 重建 / 调账 / 作废终止 / 红冲、优惠策略增删改、优惠申请提交撤销、核销 / 退款 / 红冲核销、审批全动作（提交/通过/驳回/撤回/转交/催办）全部写 sys_audit_log（oper_module=recv_pay_plan / flow_engine / discount / writeoff），记录变更前后 JSON；
2. 高危操作：计划作废终止、大额调账、红冲执行必须二次确认弹窗 + 审批引擎流转，后端强制校验流程实例通过后才允许执行业务动作；
3. node_config_json / policy_snapshot 入库前后端双重过滤 XSS 脚本字符；
4. 计划、流程、优惠、核销分摊、账单关联数据仅逻辑删除；已核销计划、已完成流程实例、红冲链记录禁止删除；
5. 计划导出、对账触发接口权限校验 + Redis 限流，防止刷库。

# 九、开发强制红线（禁止行为）

1. 禁止业务绕过审批引擎直接执行合同作废终止、大额调账、超阈值优惠生效、大额报销采购付款；
2. 禁止应收应付计划、核销分摊、资金主流水三台账金额不一致，任何单边入账视为阻断级缺陷；
3. 禁止核销/对账不写 finance_writeoff 分摊明细，直接改计划 paid_amount 隐藏账目；
4. 禁止跨 company_id 生成 / 核销 / 调整计划、挂靠账单、写核销分摊；
5. 禁止 node_config_json、policy_snapshot 不做脚本过滤直接入库；
6. 禁止已核销计划、已完成流程实例、红冲链记录物理删除；
7. 禁止前端自由文本编写审批节点公式，统一表单 JSON 配置；
8. 禁止合同生效不生成收款计划直接进入账单阶段；
9. 单据作废 / 终止禁止直接改旧计划金额，必须走红冲链（反向冲销计划 + 反向流水）；
10. 审批通过回调失败时禁止业务动作生效（事务回滚，允许人工重推）。

# 页面级全栈开发规范

> 本文档以 waterElecPay.vue（水电缴费管理页）为例，演示从需求分析到全栈文件落地的完整开发流程。
> 阅读方式：按章节顺序阅读，每个章节对应一个"开发步骤"，理解"为什么需要这个文件"。

---

## 一、页面分析：我要做什么？

### 1.1 先看前端页面（waterElecPay.vue）

开发者拿到需求时，首先看到的是前端页面需求描述。我们以实际页面代码为起点，逆向推导出需要哪些后端文件。

**页面功能拆解：**

| 功能区块 | 页面表现 | 需要的前端交互 | 对应的后端需求 |
|---|---|---|---|
| 顶部操作区 | "线下缴费"按钮，带权限控制 | 点击弹出缴费弹窗 | 需要缴费接口 |
| 搜索筛选区 | 记录类型（缴费/退费）、支付渠道（微信/支付宝/现金） | 点击搜索调用分页接口 | 需要分页查询接口 |
| 表格展示区 | 记录列表，含记录类型、金额、渠道、铺位、退费状态 | 分页加载、行操作（退费） | 需要分页查询接口 + 退费接口 |
| 缴费弹窗 | 输入账单ID → 显示账单详情 → 选择渠道 → 提交 | 账单ID变化时查询详情、表单提交 | 需要账单详情接口 + 缴费接口 |
| 退费按钮 | 仅缴费记录且未退费时显示 | 确认后调用退费接口 | 需要退费接口 |
| 路由参数 | 支持从账单页传入 billId 定位 | watch route.query.billId | 需要支持 billId 过滤的分页接口 |

### 1.2 推导结论

从页面分析直接得出需要开发的内容清单：

```
前端需要：
  确认：API 接口定义文件（waterElec.ts）— 已有，缴费部分补充
  确认：页面组件文件（waterElecPay.vue）— 已有，作为分析样本
  确认：路由配置 — 需要检查

后端需要新建/补充：
  确认：数据库表（water_elec_pay_record）— 建表 SQL
  确认：菜单+权限数据（sys_menu INSERT）— 权限 SQL
  确认：实体类（WaterElecPayRecord.java）— 数据库表映射
  确认：Mapper 接口（WaterElecPayRecordMapper.java）— MyBatis-Plus 数据访问
  确认：DTO 类（WaterElecPayDTO.java、WaterElecPayQueryDTO.java、WaterElecRefundDTO.java）— 入参封装
  确认：VO 类（WaterElecPayRecordVO.java）— 出参封装
  确认：Service 接口（WaterElecPayService.java）— 业务逻辑抽象
  确认：Service 实现（WaterElecPayServiceImpl.java）— 业务逻辑落地
  确认：Controller（WaterElecPayController.java）— HTTP 接口暴露
  确认：权限常量（PermissionConst.java 补充）— 权限标识定义
```

## 二、开发流程：从数据库到前端的完整链路

### 步骤 1：数据库表设计

**开发者的思考过程：**

> "这个页面需要记录缴费和退费，缴费记录要支持幂等提交（防止重复点击），还要支持退费操作。我需要一张表来存这些记录。"

**设计要点：**

```sql
-- 文件：upgrade_xxx_waterElec_pay.sql
-- 作用：定义 water_elec_pay_record 表结构

CREATE TABLE water_elec_pay_record (
  id              bigint unsigned NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  company_id      bigint       NOT NULL DEFAULT 0  COMMENT '所属子公司ID（多租户隔离）',
  bill_id         bigint       NOT NULL            COMMENT '关联账单ID（外键语义）',
  stall_id        bigint       NOT NULL            COMMENT '铺位ID',
  merchant_id     bigint       DEFAULT NULL        COMMENT '商户ID',
  pay_amount      decimal(12,2) NOT NULL DEFAULT 0 COMMENT '缴费/退费金额',
  pay_type        tinyint      NOT NULL DEFAULT 3  COMMENT '支付渠道 1微信 2支付宝 3线下现金',
  request_id      varchar(64)  NOT NULL            COMMENT '幂等请求ID（唯一键防重复提交）',
  record_type     tinyint      NOT NULL DEFAULT 1 COMMENT '记录类型 1缴费 2退费',
  refund_status   tinyint      NOT NULL DEFAULT 0 COMMENT '退费状态 0未退 1已退',
  refund_time     datetime     DEFAULT NULL        COMMENT '退费完成时间',
  refund_record_id bigint      DEFAULT NULL        COMMENT '退费记录ID（指向原缴费记录）',
  remark          varchar(500) DEFAULT NULL        COMMENT '备注说明',
  create_by       bigint       NOT NULL DEFAULT 0 COMMENT '操作人用户ID',
  create_time     datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_by       bigint       DEFAULT NULL,
  update_time     datetime     NULL ON UPDATE CURRENT_TIMESTAMP,
  is_delete       tinyint      NOT NULL DEFAULT 0 COMMENT '逻辑删除 0正常 1删除',
  PRIMARY KEY (id),
  UNIQUE KEY uk_company_request (company_id, request_id, is_delete),
  INDEX idx_company_id_is_delete (company_id, is_delete),
  INDEX idx_bill_id (bill_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='水电物业缴费记录表';
```

**字段设计说明：**

| 设计决策 | 原因 |
|---|---|
| company_id 必选 | 集团多租户架构，数据按子公司隔离 |
| request_id + 唯一索引 | 防止网络重发/重复点击导致重复缴费（幂等性） |
| record_type 区分缴费/退费 | 缴费和退费在同一张表，用类型字段区分 |
| refund_record_id | 退费记录指向原缴费记录ID，形成退费链条 |
| 快照字段（stall_number等） | 审计合规要求：铺位信息写入时固化 |
| is_delete 逻辑删除 | 数据不能物理删除，保留审计轨迹 |

### 步骤 3：后端实体类（Entity）

**开发者的思考过程：**

> "数据库表建好了，现在要在 Java 里建一个类来映射这张表。MyBatis-Plus 的 @TableName 注解指定表名，字段名自动驼峰映射。"

**代码文件：** gbi_platform_server/src/main/java/com/gbi/platform/entity/WaterElecPayRecord.java

```java
package com.gbi.platform.entity;

import com.baomidou.mybatisplus.annotation.TableName;
import lombok.Data;
import lombok.EqualsAndHashCode;

import java.math.BigDecimal;
import java.time.LocalDateTime;

/**
 * 水电物业缴费记录实体：water_elec_pay_record
 * 线下缴费/线上回调统一落账，requestId 唯一键保证幂等，退费反向标记
 */
@Data
@EqualsAndHashCode(callSuper = true)
@TableName("water_elec_pay_record")
public class WaterElecPayRecord extends BaseEntity {

    private Long companyId;
    private Long billId;
    private Long stallId;
    private Long merchantId;
    // 快照字段
    private String stallNumber;
    private String stallName;
    private String stallMarketName;
    private String categoryName;
    private String merchantName;
    private BigDecimal payAmount;
    private Integer payType;
    private String requestId;
    private Integer recordType;
    private Integer refundStatus;
    private LocalDateTime refundTime;
    private Long refundRecordId;
    private String remark;
    private String flowNo;
}
```

**编写要点说明：**

| 要点 | 说明 |
|---|---|
| extends BaseEntity | 继承基类获得 id、createBy、createTime、isDelete 等公共字段 |
| @TableName("water_elec_pay_record") | 指定数据库表名，驼峰命名自动映射（payAmount → pay_amount） |
| BigDecimal 存金额 | 避免浮点精度问题，金额字段一律用 BigDecimal |
| 快照字段 | stallNumber/stallName/stallMarketName/categoryName/merchantName — 写入时固化 |

**DTO 设计原则：**

| 原则 | 说明 |
|---|---|
| DTO 不继承实体 | DTO 只包含接口需要的字段，避免暴露实体内部结构 |
| 使用 @Valid 注解 | 入参校验（@NotNull、@Pattern 等），不符合规则直接返回 400 |
| requestId 格式限制 | 8-64位字母/数字/横线，前端生成格式如 WE1234567890-abc12345 |
| 分页参数校验 | pageNum≥1、pageSize 1-100，防止异常查询 |

### 步骤 9：Service 实现类

**开发者的思考过程：**

> "接口定义好了，现在写实现。分页查询比较简单，但缴费和退费涉及多步操作，需要事务控制。"

**代码文件：** gbi_platform_server/src/main/java/com/gbi/platform/service/impl/WaterElecPayServiceImpl.java

**核心逻辑说明：**

**分页查询 (page方法)：**
```
1. 构建 LambdaQueryWrapper 条件查询（记录类型、支付渠道、账单ID）
2. 调用 payRecordMapper.selectPage 分页查询
3. 批量查询操作人姓名（避免 N+1）
4. 转换为 VO 列表，填充展示文本（payTypeText、recordTypeText）
5. 返回 PageVO 封装结果
```

**缴费 (pay方法)：**
```
1. 幂等检查：checkIdempotent(companyId, requestId)
2. 查询账单并校验状态（不存在或已缴清则报错）
3. 构造缴费记录（含快照字段）
4. 插入缴费记录（record_type=1, refund_status=0）
5. 更新账单状态为"已缴"
6. 写入财务流水（flow_type=收入）
7. 核销应收计划
8. 记录审计日志
```

**退费 (refund方法)：**
```
1. 查询原缴费记录并校验权限和退费状态
2. 幂等检查
3. 构造退费记录（record_type=2, refund_status=1）
4. 插入退费记录
5. 更新原记录 refund_status=1
6. 写入财务流水（flow_type=支出，金额取反）
7. 账单状态回退为"待缴"
8. 冲减应收计划
9. 记录审计日志
```

**关键私有方法：**
- checkIdempotent(): 幂等检查，已存在则抛 BizException
- payTypeText(): 支付渠道文本转换
- buildRefundRecord(): 构造退费记录
- insertFinanceFlow(): 写入财务流水
- writeOffPlan(): 核销应收计划

```java
import com.gbi.platform.dto.WaterElecPayDTO;
import com.gbi.platform.dto.WaterElecPayQueryDTO;
import com.gbi.platform.dto.WaterElecRefundDTO;
import com.gbi.platform.service.WaterElecPayService;
import com.gbi.platform.vo.PageVO;
import com.gbi.platform.vo.WaterElecPayRecordVO;
import io.swagger.v3.oas.annotations.Operation;
import io.swagger.v3.oas.annotations.tags.Tag;
import jakarta.validation.Valid;
import lombok.RequiredArgsConstructor;
import org.springframework.security.access.prepost.PreAuthorize;
import org.springframework.web.bind.annotation.*;

@Tag(name = "水电物业-缴费管理")
@RestController
@RequestMapping("/waterElec/pay")
@RequiredArgsConstructor
public class WaterElecPayController {

    private final WaterElecPayService waterElecPayService;

    @Operation(summary = "缴费记录分页")
    @PreAuthorize("hasPermission(PermissionConst.WATER_ELEC_PAY_LIST,'')")
    @GetMapping("/page")
    public Result<PageVO<WaterElecPayRecordVO>> page(@Valid WaterElecPayQueryDTO dto) {
        return Result.success(waterElecPayService.page(dto));
    }

    @Operation(summary = "线下缴费")
    @PreAuthorize("hasPermission(PermissionConst.WATER_ELEC_PAY_ADD,'')")
    @PostMapping("/pay")
    public Result<Void> pay(@Valid @RequestBody WaterElecPayDTO dto) {
        waterElecPayService.pay(dto);
        return Result.success();
    }

    @Operation(summary = "退费")
    @PreAuthorize("hasPermission(PermissionConst.WATER_ELEC_PAY_REFUND,'')")
    @PostMapping("/refund")
    public Result<Void> refund(@Valid @RequestBody WaterElecRefundDTO dto) {
        waterElecPayService.refund(dto);
        return Result.success();
    }
}
```

**Controller 编写要点：**

| 要点 | 说明 |
|---|---|
| @RequestMapping("/waterElec/pay") | 统一路径前缀，与前端 API 路径对应 |
| @PreAuthorize | 方法级权限控制，引用 PermissionConst 中的权限标识 |
| @Valid | 触发 DTO 中的 @NotNull/@Pattern 等校验注解 |
| @Operation | Swagger 文档注解，自动生成 API 文档 |
| 返回 Result<T> | 统一响应格式，前端统一拦截处理 |

## 四、开发顺序建议

推荐开发顺序：数据库 SQL → 实体类 → Mapper → DTO → VO → 权限常量 → Service接口 → Service实现 → Controller → 前端API → 路由 → 页面

原因：
  1. 数据库先行：表结构确定后，实体类才有意义
  2. 实体先行：DTO/VO 的字段定义依赖实体
  3. Mapper 先行：Service 实现需要调用 Mapper
  4. Service 先行：Controller 依赖 Service
  5. 后端先行：前端 API 调用依赖后端接口定义
  6. 路由先行：页面组件需要在路由中注册才能访问

## 五、关键设计模式总结

### 5.1 幂等设计

问题：用户网络慢或重复点击，可能导致重复缴费
方案：requestId 唯一键 + 前端生成唯一ID

实现：
  1. 前端生成 requestId：WE + 时间戳 + 随机字符串
  2. 后端在插入前检查：SELECT COUNT FROM water_elec_pay_record WHERE company_id = ? AND request_id = ?
  3. 已存在则抛 BizException("重复提交")
  4. 数据库唯一索引 uk_company_request 提供兜底保护

### 5.2 快照字段设计

问题：铺位信息会变化（改名、调市场），历史缴费记录需要保持当时的信息
方案：写入时固化快照，后续修改不影响历史

实现：
  1. 实体类增加快照字段：stallNumber, stallName, stallMarketName, categoryName, merchantName
  2. Service 层从关联表读取当前值并写入快照字段
  3. 查询时直接读快照字段，不做运行时关联
  4. 历史数据通过 upgrade SQL 回填快照

### 5.3 财务流水联动设计

问题：缴费和退费需要同步写入财务流水表，保证账目一致
方案：Service 层在业务操作后自动写入 BizFinanceFlow

实现：
  1. 缴费：插入收入流水（flow_type=1），更新账单状态为已缴
  2. 退费：插入支出流水（flow_type=2，金额为负），账单状态回退待缴
  3. 使用 @Transactional 保证原子性

## 六、常见错误与规避

| 错误 | 原因 | 规避方法 |
|---|---|---|
| 忘记加 @Mapper 注解 | Mapper 接口不被 Spring 管理 | 创建 Mapper 时立即加 @Mapper |
| DTO 字段与前端不一致 | 前后端字段名/类型不匹配 | 先定义 VO，再反推 DTO 和前端接口 |
| 忘记加 @Transactional | 多步操作部分成功部分失败 | 涉及多表写入的操作必须加事务 |
| 快照字段未赋值 | 历史数据丢失铺位信息 | Service 层写入时显式赋值快照字段 |
| 权限标识前后不一致 | 前端 AuthBtn 与后端 @PreAuthorize 不匹配 | 统一从 PermissionConst 常量引用 |
| 忘记插入菜单数据 | 页面无法访问 | 建表 SQL 中必须包含 sys_menu INSERT |
